# `ric mcp` — Model Context Protocol server

`ric mcp` exposes ric's command surface as a Model Context Protocol server, so AI assistants like Claude can drive ric on your behalf — creating projects, syncing, running migrations, deploying — without you having to copy/paste commands into a terminal.

## Usage

```bash
ric mcp
```

This starts a JSON-RPC server on stdin and stdout following the MCP spec. You don't normally run it directly — you configure your AI assistant to launch it.

## What's exposed

The server advertises a small set of tools that mirror the ric CLI commands.

`ric_version` reports the ric CLI version and build information. The assistant can use this to confirm which build is installed before doing anything else.

`ric_sync` syncs host files into the container. As with the CLI version, the `tmp/` and `storage/` directories are excluded. The assistant uses this after editing files on your behalf to push changes into the container.

`ric_rails` runs a `bin/rails` command inside the container and syncs the results back to the host. This is what the assistant uses for generators, migrations, runner scripts, and any other one-shot Rails command.

`ric_container_start` starts the project's Docker container if it isn't already running. Useful for the assistant when it notices the dev container is stopped.

`ric_container_stop` stops the project's container — for example, before a long pause or before you reboot.

`ric_migrate` runs database migrations inside the container. This is a convenience shortcut for the common `bin/rails db:migrate` case.

`ric_deploy` performs a first-time deploy to the remote server. The assistant calls this on a fresh project; it requires `.ric/deploy.yml` to be present.

`ric_upgrade` upgrades an existing deployment on the remote server. The database and production credentials are preserved. The assistant uses this for ongoing releases after the initial `ric_deploy`.

Each tool runs in the project's current working directory — same way you'd run `ric` from the terminal.

## Configure Claude Desktop or Claude Code

In your Claude configuration — `claude_desktop_config.json` for Claude Desktop, `~/.claude/settings.json` for Claude Code — add:

```json
{
  "mcpServers": {
    "ric": {
      "command": "ric",
      "args": ["mcp"],
      "cwd": "/absolute/path/to/your/project"
    }
  }
}
```

The `cwd` field matters: ric commands assume they're run from inside a project directory.

If you switch projects often, you can either configure multiple entries (`ric-shop`, `ric-blog`) or omit `cwd` and let the assistant call `ric` from whichever directory it considers current.

## A typical session

You say: "Add a Post model with title and body, run the migration, and tell me how many posts exist."

Claude responds via `ric_rails`: generates the model and migration, runs the migration, runs a `runner` to count posts, and replies with the count.

You then say: "Ship it."

Claude responds via `ric_upgrade`: builds the new image, uploads it, migrates the database, restarts the app on your server.

## Safety notes

`ric_deploy` and `ric_upgrade` make real changes on a real server. Make sure the assistant has explicit instructions about which projects and hosts it may touch.

Master keys generated by ric are written to `.ric/keys/production.key` on your local machine. The MCP server doesn't transmit them anywhere — it's still local file access.

The MCP server runs as **you**: same filesystem permissions, same SSH credentials. There is no sandbox.
